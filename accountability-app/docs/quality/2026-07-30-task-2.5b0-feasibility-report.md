# Task 2.5B-0 Feasibility Report — Proof Image Normalization

**Date:** 2026-07-30 (Australia/Perth)  
**Scope:** local/read-only feasibility work only  
**Decision state:** **NOT PASS — both mandatory gates remain open**

This report records what can be proven from the checked-out repository, its
exact installed artifacts, official platform documentation, and one isolated
local codec-load spike. It does not authorize a function, dependency, migration,
secret, deployment, OTA, or application-code change.

## Executive decision

The proposed Edge Function remains a reasonable candidate architecture, but it
is not yet an accepted ADR.

1. `@imagemagick/magick-wasm@0.0.41` is a real Deno-capable WASM codec candidate
   and is the codec used by Supabase's current official image-manipulation
   example. Its exact published artifact was pinned and loaded locally.
2. It is **not** a bounds-only probe. `ImageMagick.read` crosses the decoder
   boundary. A separately owned, narrowly scoped JPEG/PNG/WebP parser is still
   required and must be security-reviewed before any decoder call.
3. The codec has not been proven inside the hosted Supabase runtime. Its
   14.59 MB WASM binary, broad codec surface, 256 MB memory ceiling, 2 second CPU
   ceiling, and Supabase's warning about images over 5 MB make the deployed
   feasibility test mandatory.
4. The installed Expo SDK exposes two partial transport paths, but no installed
   **public** API currently proves every client requirement. `expo/fetch` can
   authenticate, POST, cancel, inspect normalized headers, and stream a response
   body, but it buffers every supported request body before starting the native
   request. It also exposes normalized `Headers`, not a public raw duplicate-
   preserving header list. `expo-file-system` can upload a file natively and
   cancel, but returns the response body as a string and its headers as a
   `Record<string,string>`; its download task is GET-oriented and does not return
   response headers. Physical-device proof is still mandatory, and the exact
   duplicate-header rejection requirement is currently a likely blocker.

The safe present behavior therefore remains: bundled background only; local,
buddy, and route images remain fail-closed.

## Client transport findings

### Candidate A: `expo/fetch` from `expo@56.0.17`

Locally inspected implementation:

- `expo/src/winter/fetch/fetch.ts`
- `expo/src/winter/fetch/RequestUtils.ts`
- `expo/src/winter/fetch/FetchResponse.ts`

Proven from source:

- accepts request headers and POST;
- accepts an `AbortSignal` and calls the native request's cancel method;
- exposes status and `Headers`;
- exposes `ReadableStream<Uint8Array>` for response bodies;
- response chunks can be counted and written through an Expo `FileHandle`, so
  the app can abort above 4 MiB and delete the partial file;
- **request streaming is not implemented**: strings, arrays, blobs/files,
  readable streams, and multipart `FormData` are all materialized as a single
  `Uint8Array` by `normalizeBodyInitAsync` before `NativeRequest.start`;
- `blob()`, `bytes()`, `arrayBuffer()`, and `text()` are buffering APIs and must
  not be used for the canonical response;
- when native reception finishes before JavaScript starts reading,
  `startStreaming()` may return already-completed response data as one buffer.
  Therefore peak native memory and backpressure cannot be inferred from the
  TypeScript surface.

**Accurate description:** bounded buffered upload plus potentially streaming
download. It must not be called full-duplex streaming.

**Header blocker:** the public response surface is `Headers`. The source has an
internal `_rawHeaders` array, but it is not part of the public exported
contract. Depending on a private property would be an unpinned native contract
and still needs platform verification. Standard `Headers` may combine duplicate
values, so "exactly one header" cannot currently be proven for every required
header.

### Candidate B: `expo-file-system@56.0.8`

Locally inspected implementation/types:

- `expo-file-system/src/NetworkTasks.ts`
- `expo-file-system/build/NetworkTasks.types.d.ts`

Proven from source:

- `UploadTask` sends a native file as binary or multipart, accepts auth headers,
  reports progress, supports cancellation, and returns status plus headers;
- `UploadResult.body` is a **string**, and `headers` is a
  `Record<string,string>`, so binary canonical output and duplicate headers are
  not safely represented;
- `DownloadTask` writes to a managed file, supports auth headers/progress/
  cancellation, but is URL/GET-oriented and returns only `File | null`, not
  response status or response headers.

No single public FileSystem task satisfies authenticated POST upload plus binary
response-to-file plus strict response-header validation.

### `supabase.functions.invoke`

`@supabase/functions-js@2.108.2` delegates to fetch and supports a signal and
timeout, but for `image/jpeg` it falls into the default `response.text()` branch.
It is unsuitable for this binary response contract without bypassing
`invoke()` and calling the authenticated function URL with the physically
proven transport.

### Required physical Android proof

The following remain unproven until run on the installed SDK 56 staging build:

- whether `expo/fetch` preserves all gateway headers and how duplicates appear;
- whether request body copies are one, two, or more 12 MiB allocations;
- whether response events apply useful backpressure or native buffers the full
  response;
- abort latency during upload and download;
- partial-file cleanup after abort, app background, unmount, account switch,
  timeout, and process interruption;
- measured peak Java/Kotlin/native/Hermes memory for a 12 MiB upload plus a
  4 MiB response;
- exact behavior for missing, duplicate, folded, conflicting, and malformed
  `Content-Length`, `Digest`, and `X-Proof-*` headers through the Supabase
  gateway.

**Client gate status: OPEN / likely contract blocker.** If raw duplicate
preservation cannot be proven through a public pinned API, either the protocol
must be revised and independently re-audited (for example, a single
cryptographically bound manifest with a binary payload) or the native-module
ADR must be reopened. Private `_rawHeaders` is not an acceptable production
dependency without an explicit frozen Expo contract.

## Probe candidates

### Rejected: `image-size@1.2.1`

This exact version already exists transitively and parses dimensions from
bytes without pixel decode, but it is not acceptable as the security probe:

- its WebP parser reads dimensions from a fixed header slice and does not scan
  the RIFF chunk graph for `ANIM`/`ANMF`;
- it cannot prove rejection of animated WebP;
- it does not enforce this plan's complete JPEG segment, PNG chunk/CRC/order,
  truncation, polyglot, excessive-metadata, or exact-file-boundary rules;
- it is a Node-targeted package (`node >=16`), not yet deployed-runtime-proven.

### Recommended probe direction: owned bounded parser

Implement a small pure parser that recognizes only JPEG, PNG, and WebP and
never allocates a pixel buffer. It must consume the already byte-capped source
through bounded cursors:

- JPEG: validate SOI; walk length-delimited markers with overflow checks; allow
  only supported SOF markers; extract width/height/components/orientation;
  bound metadata bytes; reject multiple conflicting SOFs and trailing/polyglot
  structure according to a written grammar.
- PNG: validate signature, IHDR first/unique, dimensions/bit-depth/color type,
  bounded chunk lengths and CRCs; reject `acTL`/`fcTL`/`fdAT`; require a valid
  terminal IEND and reject trailing bytes.
- WebP: validate RIFF length exactly; walk every padded chunk with overflow
  checks; extract VP8/VP8L/VP8X bounds; reject animation flag plus `ANIM` and
  `ANMF`; reject conflicting image chunks and trailing bytes.

This probe has no external package version yet because it would be repository-
owned source. Its future source hash, tests, and reviewed commit must become
the pin. It is **not implemented or proven by this report**.

### Local load spike (not a runtime gate)

Environment: Windows, Node `24.11.1`; no Deno or Supabase CLI was installed or
used. Initializing the pinned WASM from its verified bytes produced:

- ImageMagick runtime: `7.1.2-25 Q8`;
- initialization wall time: approximately 50 ms;
- process RSS: 37,388,288 to 82,812,928 bytes (about +43.3 MiB);
- external memory: 1,796,541 to 33,395,842 bytes;
- ArrayBuffer memory: 10,515 to 14,613,884 bytes.

This proves only that the artifact loads and identifies itself. It does not
measure Supabase CPU accounting, Deno behavior, decode memory, concurrent
requests, malformed-image behavior, or production-like limits.

### Codec risks still requiring proof

- Supabase documents 256 MB maximum memory and 2 seconds CPU per request, and
  warns its WASM image example can exceed limits for complex or larger-than-5
  MB images. The plan's 12 MiB source cap therefore cannot be accepted from
  documentation alone.
- The WASM contains many decoders beyond JPEG/PNG/WebP. The owned probe and
  exact magic allowlist must be the only path to the decoder; coders/delegates
  should be disabled where the API permits.
- The artifact's `NOTICE` contains licenses for many embedded delegates,
  including copyleft components. Apache-2.0 is the package license, but legal/
  attribution review of the complete NOTICE is still required before
  distribution or hosted deployment.
- ImageMagick's vendor changelog shows `7.1.2-25` includes security fixes.
  NVD/GitHub searches did not identify an advisory declaring this exact version
  affected as of the report date, but that is not a complete software-
  composition analysis of every embedded delegate. The exact artifact still
  needs an SBOM and a vulnerability scan immediately before deployment.
- `ImageMagick.read` is a decoder call and cannot serve as the bounds-only
  parser, even if width/height properties are read immediately.
- Exact JPEG output controls (quality 85, 4:2:0, non-progressive, optimize flag,
  sRGB, metadata strip, alpha-on-white), stable same-build golden hashes,
  animation rejection, orientation, and timeout/cancellation behavior remain
  unproven.

## Required next evidence (still non-production)

1. Implement the owned pure probe and its adversarial corpus locally; obtain an
   independent security review proving no decoder allocation occurs first.
2. Bundle the exact pinned WASM plus the function with the exact Supabase CLI
   version; record final bundle bytes and dependency graph.
3. Run corpus and concurrency tests under a 256 MB process ceiling and a strict
   CPU deadline. Treat this only as preflight, not hosted proof.
4. Under a separate staging-only approval, deploy the throwaway non-routable
   feasibility function, record deployment artifact hashes, CPU, peak memory,
   timeouts, output hashes, and delete it.
5. On the physical Android staging device, test `expo/fetch` specifically,
   including maximum upload/download, native/Hermes peak memory, cancellation,
   partial cleanup, and gateway header behavior.
6. If raw duplicate-header validation remains impossible through a public API,
   stop and revise the protocol/native ADR before any product-function work.

## Final status

**ADR-2.5B remains proposed and blocked.** No production or staging state was
changed. No application code, package manifest, lockfile, secret, function, or
migration was changed. The isolated `.tmp/task-2.5b0` download/extraction
directory was removed after its checksum and measurements were recorded; this
report is the only retained research artifact.
